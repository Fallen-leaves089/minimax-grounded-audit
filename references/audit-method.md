# 审计方法

## 1. 三种检查模式

- **变更检查**：固定基准点到 `HEAD`。基准点必须能解析；diff 为空时先确认是只做回归还是改为全量检查。
- **全量检查**：当前 `HEAD` + 工作区清单。未提交改动单独列出，不因为“没有 diff”而中止。
- **无 Git 快照**：只做当前目录的只读检查，明确说明无法查看历史、基准点和精确 diff。

模式未确认前，不要进入构建、子代理或报告阶段。

## 2. 证据层级

从强到弱：

1. 当前环境实际运行并可复跑的结果；
2. 带工具状态、退出状态、cwd 和关键输出的调用；
3. 已结束后台任务及其完整输出文件；
4. 源码、配置、测试和构建产物中的直接证据；
5. 项目文档、历史报告和提交说明；
6. 通用启发式与推断。

低层级证据不能覆盖高层级事实。模型内部的思考、可见推理文本或旧摘要不是证据；只有工具结果、文件和数字才能引用。

## 3. 范围锁定

锁定范围时记录：

- 检查模式与基准点；
- MiniMax Code 中目标的实际绝对路径；
- `Bash` 实际 cwd；
- 包含和排除的目录；
- 目标平台或运行环境；
- 已知不可执行的面；
- 检查前后的工作区状态；
- 报告输出路径与外部记忆路径。

目标在 MiniMax Code 当前视图中不可见、目录清单为空或不可读时，fail-closed。不要猜测其他宿主视图。

## 4. Standards 轴

检查：

- 项目文档化的编码规范、目录约定、架构边界和命名规则；
- 现有范例是否被一致遵循；
- 明显坏味道是否与规范冲突。

仓库没有文档化规范时，把坏味道基线当作补充启发式；每条都是判断意见，不是硬性违规。不要自创项目标准。

## 5. Spec 轴

对照：

- spec、PRD、issue、验收标准；
- 已承诺但未实现的路径；
- 实现了但没有需求依据的功能；
- 做了但行为与需求不一致的部分。

spec 缺失时明说，不编需求。两轴分开记录，避免把“代码不漂亮”和“需求没完成”混为一谈。

## 6. 真实回归

至少覆盖项目实际存在的关键路径：

- 单元/集成/端到端测试；
- 生产构建与产物自检；
- 数据库迁移与幂等回归；
- 容器或部署配置校验；
- 关键用户路径冒烟；
- 失败路径和回滚路径。

MiniMax Code 的 `Bash` 支持工作目录参数；执行前记录实际目录，需要绝对路径时显式写出。长任务使用 `run_in_background` 后，用 `task_output` 查看终态和增量输出，并记录 task ID、输出位置、关键结果和执行目录。大输出首响应只保留约 24 KiB 的头部和尾部，必须用完整日志引用或 `task_output` 补齐。

前台命令超时后可能转为后台任务继续运行；看到超时提示不等于进程已结束。`/clear` 或切换会话也不保证停止后台工作。构建失败先区分环境问题和代码问题。环境问题记录绕法或未覆盖原因，不直接算 P0。

## 7. 分级口径

- **P0**：部署当天会直接爆雷。数据损坏、无法启动、认证绕过、不可恢复的发布阻断。
- **P1**：部署前必须处理。关键功能错误、迁移必失败、明显安全风险、无法回滚。
- **P2**：部署前建议处理。非关键路径缺陷、可维护性风险、监控或文档缺口。
- **P3**：卫生与可维护性。命名、格式、低风险技术债。

严重度看影响，不只看触发概率。环境限制不等于 P0；未覆盖也不等于通过。

## 8. 问题卡片

每条问题至少包含：

```text
[P0-P3] 标题
证据：file:line 或 command
影响：
建议：
验证方式：
置信度：已验证 / 观察到 / 推断
```

建议要尽量沿用项目既有范例；没有范例时，提出最小可行改动并标明是建议。不要顺手改代码。

## 9. 覆盖声明

报告必须包含：

- **已核验无问题的部分**：说明查了什么、怎么查的；
- **本轮未覆盖的部分**：说明为什么没覆盖、需要什么条件补测；
- **环境限制**：工具缺失、权限不足、网络不可用、服务不存在等；
- **历史证据边界**：旧报告、旧构建结果不能自动当成当前结果。

## 10. 输出顺序

1. 现在最该做的三件事；
2. 一句话结论；
3. P0-P3 明细；
4. 已核验项；
5. 未覆盖项；
6. 记忆结果。

面向非技术读者时，先讲影响和下一步，再解释命令和代码位置。
